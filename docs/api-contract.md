# API Contract (Proposed)

Prefix: `/api/v1`. The service exposes a REST API with OpenAPI specification automatically generated by FastAPI.

## Global conventions
- **Encoding & Media:** JSON request and response payloads (`Content-Type: application/json`).
- **Identifiers:** Canonical UUIDv4 strings for all resource IDs.
- **Timestamps:** ISO-8601 strings in UTC (e.g. `2026-10-27T12:00:00Z`).
- **Authentication:** `Authorization: Bearer <jwt-token>` header for protected endpoints.
- **Idempotency:** Sensitive write endpoints require the `Idempotency-Key: <unique-uuid-or-string>` header.
- **Pagination:** Query parameters `page` (default 1) and `page_size` (default 20, max 100) with deterministic ordering (`created_at DESC, id DESC`).
- **Error shape:** Standardized error response format:
  ```json
  {
    "error": {
      "code": "SLOT_ALREADY_BOOKED",
      "message": "The selected doctor slot is no longer available.",
      "request_id": "req_01j9a4k7..."
    }
  }
  ```

## 3. Booking and consultation (`/bookings`, `/consultations`)

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/api/v1/bookings` | Patient (`Idempotency-Key` required) | Atomically reserve slot and create consultation |
| GET | `/api/v1/bookings/{booking_id}` | Owner / Assigned Doctor / Admin | Retrieve booking status and details |
| POST | `/api/v1/bookings/{booking_id}/cancel` | Booking Owner / Admin (`Idempotency-Key` required) | Cancel an eligible booking and release its slot atomically |
| GET | `/api/v1/consultations` | Patient / Doctor scoped | List consultations filtered by caller's identity |
| GET | `/api/v1/consultations/{id}` | Patient / Assigned Doctor / Admin | Get consultation detail and medical record summary |
| POST | `/api/v1/consultations/{id}/confirm` | Assigned Doctor | Confirm appointment (`booked` → `confirmed`) |
| POST | `/api/v1/consultations/{id}/start` | Assigned Doctor | Begin consultation (`confirmed` → `in_progress`) |
| POST | `/api/v1/consultations/{id}/complete` | Assigned Doctor | Complete consultation (`in_progress` → `completed`) |
| POST | `/api/v1/consultations/{id}/no-show` | Assigned Doctor / Admin | Mark patient no-show (`confirmed` → `no_show`) |

`POST /api/v1/bookings` requires a patient access token and an `Idempotency-Key` header. Its body
contains `doctor_id` (UUID), `slot_id` (UUID), and an optional `reason` no longer than 2,000
characters. It returns the created consultation (`id`, `patient_id`, `doctor_id`, `slot_id`,
`status`, optional `reason`, `created_at`, and `updated_at`) with `201 Created`. A matching
completed retry returns the exact stored representation with `200 OK`; a reused key with a changed
body, a slot owned by a different doctor, or an unavailable slot returns `409 Conflict`. Booking
is limited to future slots whose status is `available`.

Cancellation is permitted only while a consultation remains `booked` and its slot has not started.
The owning patient or an administrator may cancel; an assigned doctor may retrieve but cannot
cancel the booking. The cancelled consultation remains in the record, its slot moves back to
`available` in the same transaction, and a repeated cancellation returns the existing cancelled
representation with `200 OK`. `POST /api/v1/consultations/{id}/cancel` provides the same atomic
cancellation functionality within the consultations namespace.

### Consultation Lifecycle State Transitions
Consultations enforce an explicit forward-only state machine:
- `booked` → `confirmed`: Triggered by the assigned doctor or admin via `POST /api/v1/consultations/{id}/confirm`.
- `confirmed` → `in_progress`: Triggered by the assigned doctor via `POST /api/v1/consultations/{id}/start`.
- `in_progress` → `completed`: Triggered by the assigned doctor via `POST /api/v1/consultations/{id}/complete`.
- `confirmed` → `no_show`: Triggered by the assigned doctor or admin via `POST /api/v1/consultations/{id}/no-show`.
- `booked` → `cancelled`: Triggered by the patient owner or admin via `POST /api/v1/bookings/{id}/cancel` or `POST /api/v1/consultations/{id}/cancel`.

Any transition outside this matrix (e.g. `booked` → `completed` or transitioning from terminal states `completed`, `cancelled`, `no_show`) returns `409 Conflict`. Simultaneous transitions are serialized via `SELECT ... FOR UPDATE` so conflicting updates cannot silently overwrite each other. Every transition enqueues an outbox event and records an audit log.

`GET /api/v1/consultations` accepts optional query parameters `status` (validated against allowed statuses), `patient_id` (admin only), `doctor_id` (admin only), `page`, and `page_size`. Non-admins have results automatically restricted to their own appointments or assigned clinical consultations.


## 4. Prescriptions (`/consultations/{id}/prescriptions`, `/prescriptions`)

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/api/v1/consultations/{id}/prescriptions` | Assigned Doctor | Create or amend prescription with line items for an eligible consultation |
| PUT | `/api/v1/consultations/{id}/prescriptions` | Assigned Doctor | Amend prescription line items and increment version |
| GET | `/api/v1/consultations/{id}/prescription` | Patient / Assigned Doctor / Admin | Retrieve prescription for a consultation |
| GET | `/api/v1/prescriptions/{id}` | Patient / Issuing Doctor / Admin | Retrieve prescription by its direct ID |

Prescription creation and amendment require an authenticated doctor who is assigned to the consultation.
The consultation must be in an eligible state (`in_progress` or `completed`); attempting to issue a prescription
for `booked`, `confirmed`, `cancelled`, or `no_show` consultations returns `409 Conflict`.

Each prescription contains optional clinical `notes` and a non-empty list of structured line items (`items`), where each item validates:
- `medicine_name`: Non-blank string (1–255 chars)
- `dosage`: Non-blank dosage specification (1–64 chars, e.g. `500mg`, `10ml`)
- `route`: Administration route (1–64 chars, e.g. `oral`, `topical`, `nasal`)
- `frequency`: Intake frequency (1–64 chars, e.g. `twice daily`)
- `duration`: Course duration (1–64 chars, e.g. `5 days`, `2 weeks`)
- `instructions`: Optional patient instructions (up to 2,000 chars)

Creating a prescription initializes `version = 1`. Amending an existing prescription increments `version` and atomically replaces line items within the same transaction. Prescription contents (medication names, dosages, instructions) are **never** logged to audit trails or outbox event payloads; only resource identifiers, version counters, and item counts are recorded.


## 5. Payments (`/consultations/{id}/payments`, `/payments`)

| Method | Path | Access | Description |
|---|---|---|---|
| POST | `/api/v1/consultations/{id}/payments` | Patient (`Idempotency-Key` required) | Initiate payment intent through mock payment provider |
| GET | `/api/v1/payments/{id}` | Patient / Assigned Doctor / Admin | Check payment status; auto-reconciles timeouts |
| POST | `/api/v1/payments/webhooks/{provider}` | Webhook Signature Verified | Idempotently process provider callback events |

### Payment Intent Initiation
`POST /api/v1/consultations/{id}/payments` requires an authenticated patient who owns the consultation, and an `Idempotency-Key` header.
- **Request body** (`PaymentCreateRequest`):
  - `amount_minor` (optional integer): Expected fee in minor currency units (paise). If provided and does not match the assigned doctor's consultation fee, returns `409 Conflict`.
  - `simulation` (optional string): Simulation mode for evaluation (`success`, `pending`, `failure`, `timeout`).
- **Response** (`PaymentResponse`, HTTP 201 Created on fresh creation; HTTP 200 OK on replayed request):
  - `id`: Unique payment record UUID.
  - `consultation_id`: Associated consultation UUID.
  - `amount_minor`: Consultation fee charged in integer minor units.
  - `currency`: Currency code (e.g. `INR`).
  - `status`: Lifecycle status (`succeeded`, `pending`, `failed`, `requires_reconciliation`).
  - `provider`: Provider identifier (`mock_provider`).
  - `provider_reference`: Simulated provider transaction ID (e.g. `mock_pi_...`).
  - `created_at` / `updated_at`: UTC timestamps.
- **Rules and Edge Cases**:
  - External provider API calls occur outside database locks.
  - Ineligible consultation states (`cancelled`, `no_show`) return `409 Conflict`.
  - Already-paid consultations (`status = succeeded`) return `409 Conflict`.
  - Unknown/timeout provider responses transition to `requires_reconciliation` instead of assuming failure.
  - Card numbers (PANs), CVVs, and raw secrets are never requested, stored, or logged.

### Payment Status Retrieval & Reconciliation
`GET /api/v1/payments/{id}` returns the current `PaymentResponse`.
- Restricted to the paying patient, assigned doctor, or administrator; unrelated callers receive `403 Forbidden`.
- If the payment is in `requires_reconciliation` status, the service queries the adapter to reconcile the transaction with the provider, updates the database state to `succeeded`, records an audit event, and returns the resolved representation.

### Provider Webhook Processing
`POST /api/v1/payments/webhooks/{provider}` processes asynchronous provider events idempotently.
- Requires `X-Webhook-Signature` header containing HMAC-SHA256 digest of request body. Missing or invalid signature returns `401 Unauthorized`.
- Supports event types: `payment.succeeded`, `payment.failed`, `payment.refunded`.
- **State transitions**:
  - `pending` → `succeeded` or `failed`
  - `requires_reconciliation` → `succeeded` or `failed`
  - `succeeded` → `refunded`
- **Idempotency**: Re-delivering a webhook for an already transitioned payment returns `200 OK` with status `"already_processed"`.
- **Invalid transitions**: Attempting an illegal transition (e.g. `failed` → `succeeded`) returns `409 Conflict`.

| Method | Path | Access | Description |
|---|---|---|---|

### Security Audit Trail (`GET /api/v1/admin/audit-logs`)
Administrative endpoint providing query and inspection access to the tamper-evident security audit trail.
- **Access control**: Restricted strictly to users with the `admin` role via `require_admin`. Non-admin callers receive `403 Forbidden`; unauthenticated callers receive `401 Unauthorized`. Accessing this endpoint records an administrative audit event (`action="admin.audit_read"`).
- **Query parameters**:
  - `action` (optional string): Exact match filter (e.g. `booking.create`, `booking.cancel`, `consultation.confirmed`, `prescription.create`, `payment.initiate`, `payment.reconciled`, `availability.create`).
  - `resource_type` (optional string): Target entity type (e.g. `consultation`, `prescription`, `payment`, `availability_slot`, `audit_log`).
  - `resource_id` (optional string): Identifier of the target resource.
  - `actor_user_id` (optional UUID): Identifier of the actor executing the action.
  - `date_from` (optional ISO-8601 UTC timestamp): Inclusive lower bound for event creation (`created_at >= date_from`).
  - `date_to` (optional ISO-8601 UTC timestamp): Inclusive upper bound for event creation (`created_at <= date_to`).
  - `page` (optional integer, default 1, min 1): Pagination page index.
  - `page_size` (optional integer, default 20, min 1, max 100): Bounded page size.
- **Ordering**: Deterministic reverse chronological order (`created_at DESC, id DESC`).
- **Response** (`AuditLogListResponse`):
  - `items`: List of `AuditLogResponse` objects (`id`, `actor_user_id`, `action`, `resource_type`, `resource_id`, `correlation_id`, `metadata`, `created_at`).
  - `page`: Current page number.
  - `page_size`: Current page size.
  - `total`: Total matching record count.
- **Sanitization & redaction**: Audit logs strictly exclude passwords, tokens, MFA secrets, credit card data (PAN/CVV), prescription clinical contents (items, dosage, notes, diagnosis), and raw request bodies.
- **Transactional atomicity policy**: Audit records emitted during business operations (bookings, cancellations, availability changes, consultations, prescriptions, payments) are enlisted in the active database transaction without an independent commit. If the operation succeeds, the audit trail commits atomically; if the operation fails or rolls back, the audit record is rolled back, preventing misleading 'ghost' entries.

## HTTP status code semantics
- `200 OK`: Request succeeded.
- `201 Created`: Resource successfully created.
- `400 Bad Request`: Malformed payload or invalid parameters.
- `401 Unauthorized`: Authentication credentials missing or invalid.
- `403 Forbidden`: Authenticated, but lacking permissions for resource.
- `404 Not Found`: Resource does not exist (or concealed by policy).
- `409 Conflict`: Slot already booked, idempotency payload mismatch, or state conflict.
- `422 Unprocessable Entity`: Schema/field validation error.
- `429 Too Many Requests`: Rate limit threshold exceeded.
- `500 Internal Server Error`: Internal server error (redacted from client).
- `503 Service Unavailable`: Temporary upstream dependency outage.
